# Личная CRM

Приложение для контактов людей, которых знаю лично: кто это, откуда знакомы, телефон, почта и заметки после разговоров. Идея и сценарии — в `specs/01-продуктовая-идея.md`.

## Что умеет

- Список всех контактов по алфавиту: сначала видны первые 50, следующие подгружаются сами, когда долистываешь до конца
- Стрелка в правом нижнем углу возвращает в начало списка
- Поиск по имени, типу кузова и вместимости машины: регистр не важен, слова можно в любом порядке, «е» и «ё» считаются одной буквой; все совпадения показываются сразу
  - тип кузова: «тент», «реф», «цмф», «изотерм» и т. д.
  - тонны: «5 тонн» или «5т» — ровно 5 т; «от 5 тонн», «5 тонн и больше», «5+ т» — 5 т и больше; «до 5 тонн», «5 тонн и меньше» — 5 т и меньше; «от 5 до 10 тонн»
  - кубы — так же: «82 куба», «от 80 кубов», «до 40 м³»
  - всё можно сочетать: «Иванов тент от 5 тонн» найдёт тенты Ивановых от 5 т; слово «вместимость» можно писать, его поиск пропускает
- Добавление контакта: он сразу появляется первым в списке и подсвечивается, а после обновления страницы встаёт на своё место по алфавиту
- Карточка контакта: данные, машина (тонны, кубы, тип кузова), правка, заметки с датой — новые сверху
- Машина видна и в списке, под описанием контакта: «20 т · 82 м³ · Тент»
- Удаление контакта вместе со всеми его заметками — после подтверждения

Данные лежат в базе PostgreSQL, поэтому в любом браузере по одному адресу видны одни и те же контакты.

## Что нужно на компьютере

- Docker Desktop — в нём работает база данных
- Node.js 20.9 или новее
- pnpm

## Первый запуск

1. Скопировать `.env.example` в `.env` и заполнить значения: имя пользователя, пароль и название базы можно придумать любые, порт — `5432`.
2. Запустить Docker Desktop и поднять базу:

   ```
   docker compose up -d
   ```

3. Установить зависимости и создать таблицы:

   ```
   pnpm install
   pnpm db:migrate
   ```

4. По желанию — наполнить базу тестовыми контактами:

   ```
   pnpm db:seed
   ```

5. Собрать и запустить приложение:

   ```
   pnpm build
   pnpm start
   ```

6. Открыть в браузере http://localhost:3000

## Обычный запуск

Docker Desktop должен быть запущен — база поднимется сама. Дальше:

```
pnpm start
```

Остановить приложение — `Ctrl+C` в том же окне терминала.

После изменений в коде перед `pnpm start` нужно снова выполнить `pnpm build`. Для разработки удобнее `pnpm dev`: изменения видны сразу, без сборки.

Если в обновлении появились новые файлы в папке `drizzle`, перед запуском нужно выполнить `pnpm db:migrate`: без этого в базе не будет новых полей.

## Тестовые данные

`pnpm db:seed` добавляет 1000 вымышленных контактов и заметки к ним. Примерно у трети контактов есть машина: от «Газели» на 1,5 т до трала на 40 т. В поле «Кто это» — люди из мира перевозок: у владельцев машин описание подходит к их машине («Трал, возит спецтехнику»), остальные — механики, склады, экспедиторы, грузоотправители. Телефоны начинаются с несуществующего кода `+7 000`, почта — на служебных доменах `example.com`, `example.org`, `example.net`, поэтому ни один тестовый контакт не ведёт к настоящему человеку.

Команда работает только с пустой базой: если контакты уже есть, она ничего не добавит.

## Сервер

Лендинг и приложение работают на одном VPS с Ubuntu 24.04: лендинг — https://volki-lzkv.ru, приложение — https://app.volki-lzkv.ru. Сервер общий: чужие настройки на нём не меняем, только добавляем свои. На лендинге пока заглушка «Скоро здесь будет сайт», приложение выкатывается само — см. «Выкатка».

Вход — `ssh crm`, по ключу. Адрес сервера и имя пользователя записаны на компьютере в `~/.ssh/config` под именем `crm`. У пользователя есть права sudo, sudo спрашивает его пароль.

Что уже настроено:

- Вход под root и вход по паролю выключены, пускает только по ключу. Правила — в `/etc/ssh/sshd_config.d/10-crm-hardening.conf`. Этот файл должен идти по алфавиту раньше файла хостинга `40-hosting.conf`: SSH берёт первое значение, которое прочитал
- Файрвол ufw: открыты только порты 22 (SSH), 80 и 443 (сайт). Проверить — `sudo ufw status`
- Обновления безопасности ставятся сами каждый день, без автоматической перезагрузки
- Docker. Он открывает порты контейнеров в обход ufw, поэтому порты по умолчанию открываются только на `127.0.0.1`, а наружу их отдаёт nginx. Логи контейнеров — не больше 30 МБ на контейнер. Настройки — в `/etc/docker/daemon.json`
- nginx раздаёт оба адреса, http перенаправляет на https. Запросы по IP-адресу и на чужие имена отклоняет
- Один сертификат Let's Encrypt на оба адреса. Продлевается сам по таймеру `certbot.timer`, после продления nginx перечитывает сертификат

Docker, nginx и сертификат ставит скрипт `deploy/server/setup.sh`, настройки nginx и заглушка лежат рядом с ним. Запуск — скопировать папку на сервер и запустить скрипт через sudo:

```
tar -C deploy -cf - server | ssh crm "mkdir -p ~/server-setup && tar -C ~/server-setup --strip-components=1 -xf -"
ssh -t crm "sudo bash ~/server-setup/setup.sh"
```

Повторный запуск безопасен: готовые шаги скрипт пропускает, а настройки nginx для лендинга и приложения, если они уже есть на сервере, не перезаписывает.

## Выкатка

Каждый push в ветку `main` сам выкатывает новую версию на https://app.volki-lzkv.ru, обычно за несколько минут. Ход выкатки виден на GitHub: вкладка Actions, workflow «Deploy».

Что происходит:

1. GitHub собирает образ приложения по `Dockerfile` и кладёт его в GitHub Container Registry (`ghcr.io/zarazzza36/personal-crm`). Тег образа — SHA коммита
2. GitHub заходит на сервер под пользователем `deploy` и копирует туда скрипты из `deploy/app`
3. Скрипт `deploy.sh` на сервере скачивает образ, применяет миграции базы в отдельном разовом контейнере, запускает новую версию и проверяет, что https://app.volki-lzkv.ru/health отвечает 200
4. Упали миграции — новая версия не запускается, работает прежняя. Не прошла проверка `/health` — выкатка красная, новая версия остаётся запущенной. Сам скрипт ничего не откатывает
5. После удачной выкатки на сервере остаются только два образа приложения: текущий и предыдущий

На сервере:

- Папка приложения — `/home/deploy/personal-crm`: `compose.yaml`, скрипты, `.env` с паролем базы (права 600), `current-image` и `previous-image` — какая версия работает сейчас и какая была до неё
- База PostgreSQL работает в Docker рядом с приложением, данные — в томе `prod_crm-postgres-data`. Наружу база не открыта
- Приложение слушает только `127.0.0.1:3100`, снаружи его отдаёт nginx
- Все контейнеры — в проекте docker compose `prod`, имена приложения начинаются с `crm-`: проект общий с лендингом

Откат — только вручную. Команда возвращает предыдущий образ:

```
ssh -t crm "sudo -u deploy bash /home/deploy/personal-crm/rollback.sh"
```

Миграции при откате не отменяются: прежняя версия работает с текущей схемой базы.

Полезные команды на сервере, после `ssh crm`:

| Команда | Что делает |
| --- | --- |
| `sudo docker ps` | Какие контейнеры запущены |
| `sudo docker logs --tail 100 prod-crm-app-1` | Последние логи приложения |
| `sudo cat /home/deploy/personal-crm/current-image` | Какая версия работает |

Подготовка сервера к выкатке делается один раз и уже сделана. Скрипт `deploy/server/setup-deploy.sh` создаёт пользователя `deploy`, кладёт ему SSH-ключи из файла и переключает nginx с заглушки на приложение:

```
sudo bash ~/server-setup/setup-deploy.sh ~/server-setup/deploy-keys.pub
```

Файл `.env` в `/home/deploy/personal-crm` создаётся руками, в нём три строки: `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB`. Пароль — только латинские буквы и цифры: он попадает в адрес подключения к базе.

Настройки на GitHub (Settings → Secrets and variables → Actions): секрет `DEPLOY_SSH_KEY` — ключ, с которым GitHub заходит на сервер; переменные `DEPLOY_HOST`, `DEPLOY_USER` и `DEPLOY_KNOWN_HOSTS` — адрес сервера, пользователь и отпечаток сервера.

## Как устроено

- `src/app` — страницы: список контактов и карточка контакта
- `src/app/actions.ts` — сохранение контактов и заметок, подгрузка списка; выполняется на сервере
- `src/app/globals.css` — дизайн-токены, как на лендинге: цвета, размеры текста, скругления, тени. Размеры в интерфейсе задаются только через них; новое имя размера нужно добавить ещё и в `src/lib/utils.ts`
- `src/components` — части интерфейса; в `src/components/ui` — компоненты shadcn/ui
- `src/db` — схема таблиц, запросы к базе, тестовые данные
- `src/lib/contact-search.ts` — как поиск понимает фразы про тонны и кубы; `src/lib/body-types.ts` — типы кузова и их другие названия для поиска
- `drizzle` — миграции базы; `src/db/migrate.mts` применяет их на сервере
- `src/app/health` — адрес `/health` для проверки после выкатки: 200, если приложение работает и видит базу
- `Dockerfile` — как собирается образ приложения
- `.github/workflows/deploy.yml` — выкатка после push в `main`
- `deploy/app` — скрипты выкатки и `compose.yaml`, их выкатка копирует на сервер; `deploy/server` — разовая подготовка сервера
- `specs` — описание продукта

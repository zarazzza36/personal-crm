# Design

## Context

Мотивация и объём — в `proposal.md`, поведение — в `specs/contact-groups/spec.md`.

Сейчас в базе две таблицы: `contacts` и `notes`. Браузер к базе не обращается: чтение — серверные компоненты и `src/db/queries.ts`, запись — server actions в `src/app/actions.ts`. Главная (`src/app/page.tsx`) рендерится на сервере: шапка с поиском, блок «Пора связаться», `ContactList`. Запрос поиска живёт в адресе (`/?q=`), `SearchInput` меняет его через `router.replace`. Без запроса список грузится частями по 50 (`listContactsPage` с курсором по имени и id), при поиске — всё найденное сразу (`searchContacts`). Окна «Новый контакт» и «Изменить контакт» — одна форма `ContactForm`; её текстовые поля собираются по `contactInputSchema`. В `src/components/ui` уже есть `Checkbox` и `AlertDialog` на Base UI. Порядок по алфавиту везде — `collate "ru-x-icu"`.

Автотестов в проекте нет: Vitest и Playwright названы в стеке `CLAUDE.md`, но не подключены. e2e и CI пользователь отложил на потом.

## Goals / Non-Goals

**Goals:**

- Одна правда о том, кто в какой группе: таблица связей; метки, фильтр и числа на странице «Группы» читаются из неё
- Уникальность названия и «найди или создай» решает база, а не проверка перед записью: нет гонки между двумя вкладками
- Код групп, который работает с данными, можно проверить тестом на настоящей базе без моков и без Next.js

**Non-Goals:**

- Цвета и значки групп, вложенные группы, ручной порядок групп
- Выбор нескольких групп в фильтре сразу, фильтр «без группы»
- Поиск по названию группы
- Метки групп в блоке «Пора связаться»
- Playwright, e2e-тесты и CI — следующей задачей

## Decisions

### Две таблицы

- `groups`: `id` (identity), `name text not null`, `created_at`. Уникальный индекс `groups_name_key` на `lower(name collate "ru-x-icu")`
- `contact_groups`: `contact_id` → `contacts.id`, `group_id` → `groups.id`, оба `on delete cascade`; первичный ключ `(contact_id, group_id)`, отдельный индекс на `group_id` для фильтра и чисел

Удаление контакта или группы само удаляет связи, контакты при удалении группы не трогаются. Одна миграция `drizzle/0004_*.sql`, только новые таблицы.

`lower()` с ICU-сортировкой понижает регистр кириллицы одинаково при любой локали сервера базы, поэтому «Теннис» и «теннис» совпадут и на локальной базе, и на сервере.

Отвергнуто: массив названий групп в `contacts`. Переименование и удаление группы пришлось бы проходить по всем контактам, а уникальность и число контактов в группе — считать руками.

Отвергнуто: регистронезависимая ICU-сортировка (`deterministic = false`) на колонке. Это ещё один объект в схеме ради того, что делает индекс по выражению.

### Название группы

`src/lib/group-input.ts`: `groupNameSchema` — `trim`, не пусто («Укажите название группы»), не длиннее 50 («Не длиннее 50 символов»). Одна схема и в браузере (окно, карточка — чтобы показать ошибку без запроса), и в server actions. `groupNameKey(name)` — `toLocaleLowerCase("ru")`: по нему окно и карточка находят уже существующую группу, не спрашивая сервер.

### Код данных — в `src/db/groups.ts`

Server actions в `actions.ts` остаются тонкими: проверить ввод → вызвать функцию из `src/db/groups.ts` → `revalidatePath("/", "layout")`. Функции работы с данными не зависят от Next.js, их и проверяют тесты:

- `listGroups()` — id, название, число контактов; по алфавиту
- `getGroup(id)` — для фильтра на главной; нет — `undefined`
- `createGroup(name)` — `insert … on conflict do nothing returning id`; ничего не вернулось — `{ ok: false, error: "Такая группа уже есть" }`
- `renameGroup(id, name)` — нарушение уникальности (код `23505`) превращается в ту же ошибку. Смена только регистра той же группы проходит: индекс сравнивает с другими строками
- `deleteGroup(id)` — связи удаляет каскад
- `findOrCreateGroup(tx, name)` — `insert … on conflict do nothing`, затем выборка по `lower(name collate "ru-x-icu")`; так «Новая группа» с названием существующей берёт её
- `setContactGroups(tx, contactId, { groupIds, newGroupNames })` — для окна контакта: заменяет связи контакта целиком. Связи создаются `insert … select` только для групп, которые есть в базе, поэтому id удалённой в другой вкладке группы пропускается без ошибки
- `setContactGroupMembership(contactId, groupId, member)` — для галочки в карточке: передаётся нужное состояние, а не «переключить». Next.js выполняет server actions одной вкладки по очереди, поэтому при «отметили и сразу сняли» побеждает последнее нажатие
- `addContactToNewGroup(contactId, name)` — «найди или создай» и связь, в одной транзакции

### Окно контакта: поле «Группы»

`ContactForm` получает список всех групп пропсом: на главной его уже грузит фильтр, в карточке — редактор групп. Поле — список `Checkbox` с `name="groupIds"` и `value=id`, под ним «Новая группа» и «Добавить». Добавленные названия живут в состоянии формы и уходят скрытыми полями `newGroupNames`, отмеченными; в базу — только по «Сохранить». Enter в поле «Новая группа» перехватывается (`preventDefault`) и работает как «Добавить», а не как отправка формы. Название существующей группы (по `groupNameKey`) отмечает её.

`createContact` и `updateContact` сохраняют контакт и вызывают `setContactGroups` в одной транзакции. При ошибке в другом поле состояние формы возвращает и отмеченные группы, и добавленные названия — галочки не сбрасываются.

`contactFormFields` по-прежнему строится из `contactInputSchema` — только текстовые поля. Группы проверяет отдельная `contactGroupsInputSchema` (`groupIds: number[]`, `newGroupNames: string[]` через `groupNameSchema`).

Отвергнуто: создавать группу в базе сразу по «Добавить» в окне. Тогда «Отмена» оставляла бы пустые группы, а по спеке «Отмена» не сохраняет ничего.

### Карточка: строка «Группы»

Первая строка в данных контакта, перед «Откуда знакомы». Метки — по алфавиту, рядом кнопка «+». Она открывает `Popover` из shadcn/ui (`pnpm dlx shadcn@latest add popover`, на уже подключённом Base UI, новой библиотеки нет) со списком `Checkbox` и полем «Новая группа». Клиентский компонент `src/components/contact-groups-editor.tsx`: отмеченные группы — `useOptimistic`, галочка и метка меняются сразу; каждое нажатие — `setContactGroupMembership` в переходе. Ошибка — оптимистичное состояние откатывается, рядом «Не удалось сохранить, попробуйте ещё раз», как у «Пообщались».

### Главная: метки в строке

`contactListColumns` в `queries.ts` получает `groupNames: string[]` — коррелированный подзапрос `coalesce(array_agg(name order by name collate "ru-x-icu"), '{}')` по `contact_groups`. Его отдают `listContactsPage`, `searchContacts` и `getContactListItem`, поэтому метки есть и в первой странице, и в подгруженных частях, и у только что добавленного контакта. `ContactRow` рисует строку `groupNames.join(" · ")` под описанием, с `truncate`; пустой массив — строки нет.

### Главная: фильтр

- Группа в адресе: `/?group=12`, вместе с поиском — `/?q=иван&group=12`. `parseGroupId` по образцу `parseContactId`; затем `getGroup` — нет группы, значит нет фильтра
- Адрес главной собирает одна функция `contactsUrl({ query, groupId })` в `src/lib/contact-list.ts`: ею пользуются и `SearchInput` (сейчас он теряет бы `group`, собирая `/?q=` руками), и кнопки фильтра. Кнопки — `Link` с `replace` и `scroll={false}`, как поиск: история браузера не копит каждое нажатие
- `listContactsPage(cursor, limit, groupId)` и `searchContacts(query, groupId)` добавляют условие `exists (select 1 from contact_groups …)`. `loadContactsPage` и `ContactList` получают `groupId`, чтобы подгрузка при прокрутке шла по той же группе
- Счётчик: без группы и запроса — «Всего: N»; иначе «Найдено: X из N». С группой без запроса список приходит частями, поэтому X — `countContacts(groupId)`, а не длина первой страницы
- Пустые тексты: «В группе «…» пока никого нет»; с запросом — «Никого не нашлось по запросу «…» в группе «…»»
- «Пора связаться» не загружается, если есть запрос или группа
- Ряд фильтра — серверный компонент под поиском в липкой шапке: кнопки в одну строку с `overflow-x-auto`, справа, вне прокрутки, — ссылка «Группы». Так на телефоне ссылка видна при любом числе групп, а вбок прокручивается только ряд
- Добавление контакта, как и сейчас, ведёт на `/?added=…` — фильтр и поиск снимаются

### Страница «Группы»

`src/app/groups/page.tsx` — серверная страница по образцу карточки: ссылка «Все контакты», заголовок, поле «Новая группа» с «Создать», список групп «Теннис · 12 контактов». Строка группы — клиентский компонент: «Переименовать» превращает название в поле с «Сохранить» и «Отмена» (Esc — тоже отмена); «Удалить» — `AlertDialog` с текстом из спеки, фокус сначала на «Отмена», как у удаления контакта. Число контактов — `formatContactCount(n)` в `src/lib/format.ts` через уже готовые `Intl.PluralRules`: «1 контакт», «3 контакта», «5 контактов».

### Тесты: Vitest на настоящей базе

- Vitest — последняя стабильная версия на момент установки, только `devDependencies`; скрипт `pnpm test`. Других библиотек для тестов нет
- Тесты лежат рядом с кодом: `src/**/*.test.ts`
- Отдельная база: имя рабочей из `DATABASE_URL` с суффиксом `_test`, в том же контейнере Docker. `.env` не меняется, новых секретов нет. `vitest.global-setup.ts` создаёт базу, если её нет, и применяет миграции из `drizzle/` тем же `migrate`, что и `src/db/migrate.mts`. `vitest.setup.ts` в каждом процессе тестов подменяет `DATABASE_URL` на тестовую до первого импорта `@/db`
- Перед каждым тестом таблицы очищаются (`truncate … restart identity cascade`); очистка отказывается работать, если имя базы не кончается на `_test`, — рабочие контакты тест не тронет даже при ошибке в настройке
- Файлы тестов идут по очереди (`fileParallelism: false`): база одна на всех
- `server-only` в тестах указывает на свой `empty.js`, `@/` — на `src/`, как в `tsconfig.json`
- Что тестируется сейчас: проверка названий, функции `src/db/groups.ts`, запросы списка в `queries.ts`, `contactsUrl`, `formatContactCount`. Сценарии спеки про экраны (Enter в поле, выделенная кнопка, прокрутка ряда на телефоне, откат галочки без связи) проверяются руками в Chrome; e2e-тесты на них появятся вместе с Playwright

Отвергнуто: тесты компонентов в jsdom (Testing Library). Это новые библиотеки, а сценарии экранов честнее проверит Playwright в настоящем браузере.

### Тестовые данные

`src/db/seed.ts`: группы «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики»; примерно треть контактов в одной или двух из них. Свой генератор случайных чисел с отдельным зерном, как у частоты общения: имена, заметки и частоты у контактов остаются прежними.

## Risks / Trade-offs

- [Коррелированный подзапрос меток на каждую строку] → строк на странице 50, по индексу первичного ключа `contact_groups`; при поиске на 1000 контактов — тоже доли миллисекунды на строку
- [Ряд кнопок при десятках групп длинный] → прокручивается вбок только он; если групп станет очень много, понадобится другой выбор — это будет отдельная доработка
- [Подмена `DATABASE_URL` в тестах не сработала] → очистка проверяет имя базы и падает раньше, чем что-то удалит
- [Процесс тестов не завершается из-за открытого пула базы] → закрыть пул в `afterAll` общей настройки
- [Метка удалённой группы ещё видна в открытой вкладке] → после любого изменения групп `revalidatePath("/", "layout")`; в чужой вкладке — до обновления страницы, как и с контактами сейчас

## Migration Plan

Миграция `0004` только создаёт две таблицы, данные не меняются. Выкатка — как обычно: разовый контейнер применяет миграции до старта нового образа. Откат образа вручную безопасен: прежняя версия про новые таблицы не знает и не читает их.

# Design

## Context

Контакты — таблица `contacts`, заметки — `notes` с `created_at` и индексом `notes_contact_id_idx`. Заметки можно только добавлять: правки и удаления заметок нет, поэтому «последняя заметка» меняется только вперёд. Браузер к базе не обращается: чтение — серверные компоненты и `src/db/queries.ts`, запись — server actions в `src/app/actions.ts`.

Главная (`src/app/page.tsx`) рендерится на сервере при каждом запросе: шапка с поиском, затем `ContactList`. Пока есть запрос `q`, она показывает только найденное. Окна «Новый контакт» и «Изменить контакт» — одна форма `ContactForm` (`src/components/contact-dialog.tsx`), её поля берутся из `contactInputSchema` (`src/lib/contact-input.ts`); тип кузова — образец необязательного списка (`bodyTypes`, `BodyTypeField`). Всё время в приложении московское (`appTimeZone` в `src/lib/moscow-time.ts`). Автотестов в проекте нет.

## Goals / Non-Goals

**Goals:**

- Один источник правды для срока: блок на главной и строка в карточке считают его одним и тем же выражением
- Никаких фоновых задач и пересчётов: срок вычисляется при чтении из того, что уже лежит в базе

**Non-Goals:**

- Уведомления о том, что пора связаться: ни всплывающих в приложении, ни вне его
- Своя частота («раз в две недели»), «отложить», отмена отметки «Пообщались»
- Частота в строках общего списка, поиск и фильтр по частоте
- Обновление блока у открытой вкладки в полночь без перезагрузки

## Decisions

### Два поля в `contacts`, последняя заметка — из `notes`

- `contact_frequency` — enum `contact_frequency` (`week`, `month`, `quarter`, `year`), null — не задано. Значения и русские названия — в `src/lib/contact-frequency.ts`, как типы кузова в `body-types.ts`
- `contact_frequency_set_at timestamptz` — когда задали текущую частоту; null, когда частоты нет. Нужно только контакту без заметок

Последняя заметка — `max(notes.created_at)` по контакту, считается в запросе по индексу `notes_contact_id_idx`.

Отвергнуто: хранить `last_note_at` в `contacts` и обновлять при сохранении заметки. Это второй источник правды, который надо держать в согласии с `notes` (тестовые данные, ручные правки в базе), а выигрыш нулевой: контактов с частотой у одного человека — десятки, максимум сотни.

### Когда задали частоту — решает база

`createContact` пишет `contact_frequency_set_at = now()`, если частота задана. `updateContact` пишет его одним выражением в том же `UPDATE`, по старому значению строки: частота не изменилась — прежнее значение; стала null — null; другая — `now()`. Сохранение контакта с той же частотой отсчёт не сбрасывает, а гонки между чтением и записью нет.

### Срок — одно SQL-выражение

В `src/db/queries.ts` — общее выражение, его используют и запрос блока, и запрос карточки:

- день начала = московская дата `coalesce(последняя заметка, contact_frequency_set_at)`: `(… at time zone 'Europe/Moscow')::date`
- день срока = день начала + `interval '7 days'` / `'1 month'` / `'3 months'` / `'1 year'`, приведённое к `date`. PostgreSQL сам прижимает к концу месяца: `2027-01-31 + 1 month = 2027-02-28`, как требует спека
- сегодня = `(now() at time zone 'Europe/Moscow')::date`
- пора = день срока ≤ сегодня; дней без общения = сегодня − московская дата последней заметки, null без заметок

Отвергнуто: считать срок в TypeScript. Календарные месяцы с прижатием к концу месяца и московские даты пришлось бы писать самим, а сортировку и отбор «пора» — всё равно делать после загрузки всех контактов с частотой. В SQL это готовая арифметика дат, и отбор с сортировкой — в том же запросе.

### Запросы

- `listDueContacts()` — контакты с частотой, у которых пора; поля: id, имя, частота, день срока, дней без общения. Порядок: день срока по возрастанию, затем имя в русском порядке и id — как у общего списка. Возвращает всех: их немного, а «Показать всех» раскрывает без второго запроса
- `getContact(id)` дополнительно отдаёт частоту, день срока и признак «пора» для строки в карточке

### Блок на главной

Серверный `page.tsx` без поискового запроса загружает `listDueContacts()` параллельно с первой страницей списка и рисует блок над `ContactList` в той же колонке. Пустой результат или поиск — блока нет. Сам блок — клиентский компонент `src/components/keep-in-touch.tsx`: ему нужно только состояние «раскрыт/свёрнут», оно не сохраняется и после перезагрузки сбрасывается. Строка — ссылка на карточку: имя, под ним частота и дни. Цвета, шрифты и отступы — существующие дизайн-токены.

### Тексты

- Названия частот — в `src/lib/contact-frequency.ts`: «Раз в неделю» и т. д.; в строке блока — со строчной буквы
- `formatDays(n)` в `src/lib/format.ts` через `Intl.PluralRules("ru")`: «21 день», «22 дня», «25 дней»
- Дата срока в карточке: «15 ноября» в текущем году, «3 марта 2027 г.» — в другом. День срока приходит из базы как дата без времени, форматируется без сдвига часового пояса

### Поле в форме

`contactFrequency` добавляется в `contactInputSchema`: пустая строка → null, иначе одно из четырёх значений. Поле в форме — `Select` с пунктом «Не задано», как «Тип кузова», после «Почты». Форма собирает поля из схемы, так что новое поле подхватывается само.

### Свежесть после заметки и правки

`updateContact` и `deleteContact` уже вызывают `revalidatePath("/", "layout")`. `addNote` сейчас обновляет только текущую страницу (`refresh()`); к нему добавляется `revalidatePath("/")`, чтобы после заметки главная, открытая ссылкой или кнопкой «Назад» браузера, показала блок без этого контакта.

### Отметка «Пообщались» — обычная заметка

- Текст заметки — константа `TALKED_NOTE_BODY = "Пообщались"` в `src/lib/contact-frequency.ts`. Чекбокс в блоке и кнопка в карточке вызывают существующий `addNote(contactId, TALKED_NOTE_BODY)`: выражение срока, `revalidatePath("/")` и `refresh()` уже работают для любой заметки. Нового server action и новых полей в базе нет
- Строка блока: ссылка на карточку (имя, частота, дни) и рядом, вне ссылки, чекбокс с подписью «Пообщались» — интерактивный элемент внутри ссылки недопустим. Строка скрывается сразу через `useOptimistic` в переходе с `addNote`; когда переход закончится, сервер уже прислал блок без контакта. Пока сохраняется, чекбокс недоступен, поэтому второй заметки не будет. Ошибка → оптимистичное скрытие откатывается, строка на месте с текстом «Не удалось сохранить, попробуйте ещё раз»
- Чекбокс — компонент `Checkbox` из shadcn/ui в `src/components/ui`: он построен на Base UI, который уже в проекте, новой библиотеки нет
- Карточка: клиентская кнопка «Пообщались» в строке «Как часто общаться», только при заданной частоте. Пока сохраняется — недоступна; `refresh()` перерисовывает строку срока и список заметок. Ошибка — тот же текст рядом с кнопкой

Отвергнуто: отдельное поле «последний разговор» в `contacts`. Это второй источник «последнего общения» рядом с заметками, а отметка должна быть видна в истории заметок.

### Тестовые данные

`pnpm db:seed` задаёт частоту примерно десятой части контактов, от «раз в неделю» до «раз в год», и `contact_frequency_set_at` = дата добавления контакта. Частоты берутся из своего генератора случайных чисел, как машины: люди и заметки остаются прежними. Заметки в тестовых данных разбросаны по прошлому, поэтому часть контактов с частотой сразу в блоке, часть — нет.

## Risks / Trade-offs

- Вкладка открыта через полночь → блок и карточка покажут вчерашнее состояние до перезагрузки или перехода по ссылке. Для личной CRM приемлемо
- `revalidatePath` в server action сбрасывает клиентский кеш всех посещённых страниц → лишние запросы при переходах, для одного пользователя незаметно
- Контактов с частотой станет тысячи → запрос блока считает `max(created_at)` по каждому из них, это по-прежнему один запрос по индексу; если станет медленно — тогда денормализовать
- Отметку «Пообщались» нельзя отменить, а удаления заметок в приложении нет → ошибочная отметка остаётся в истории, и срок от неё начинается заново. Так решил пользователь: без отмены и без подтверждения
- Автотестов нет → проверка по сценариям спеки руками в браузере. Даты, которые нельзя дождаться (8 октября, конец февраля), проверяются заметками с `created_at` в прошлом в локальной базе и SQL-запросом выражения срока на фиксированных датах

## Migration Plan

- `pnpm db:generate` создаёт `drizzle/0003_*.sql`: тип `contact_frequency` и два nullable-поля в `contacts`. У существующих контактов оба null — частота не задана, в блок никто не попадает
- На сервере миграция идёт до старта нового образа, как в каждой выкатке
- Откат: `rollback.sh` возвращает предыдущий образ, он не знает новых полей и не трогает их. Миграция не отменяется

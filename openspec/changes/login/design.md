# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/user-auth`, `specs/data-ownership` и `specs/contact-groups`.

Сейчас пользователей нет. Чтение данных — функции в `src/db/queries.ts`, `src/db/contacts.ts` и `src/db/groups.ts`. Запись — server actions в `src/app/actions.ts`, они проверяют ввод через zod и вызывают эти функции. Ни одна функция не знает, чья запись. Корневой `src/app/layout.tsx` оборачивает все страницы в `Reminders` (каждые 15 секунд опрашивает `loadReminders`) и `SiteHeader` (справа «ДЛЯ ЛОГИСТОВ»). Включён `cacheComponents`: всё, что читает запрос (cookies, headers), должно стоять под `<Suspense>`. Своих кешей (`use cache`) в коде нет, так что общий кеш не может отдать чужие данные.

База: `contacts`, `notes` (каскадно от контакта), `groups` с уникальным индексом `groups_name_key` на `lower(name collate "ru-x-icu")`, `contact_groups`. Миграции — SQL из `drizzle-kit generate`, на сервере их применяет `src/db/migrate.mts` в разовом контейнере `crm-migrate` до старта нового образа. Мигратор Drizzle применяет все новые миграции в одной транзакции. Перед миграциями `deploy.sh` снимает бэкап.

Тесты: Vitest на настоящей базе `*_test` (`src/db/*.test.ts`, фабрики в `src/test/factories.ts`), Playwright на собранном приложении и базе `*_e2e_test`. Тесты кладут строки в базу напрямую. Почтовой заглушки пока нет ни локально, ни в CI.

Репозиторий публичный: почта владельца не должна попасть в git.

## Goals / Non-Goals

**Goals:**

- Владелец данных проверяется в одном месте на каждом уровне: каждая функция работы с базой требует `userId`, каждый server action берёт его только из сессии
- Правила входа (почта, лимит, отмена старых ссылок) работают одинаково для формы и для прямого запроса к серверу, потому что живут в одном хуке Better Auth
- Одна и та же сборка приложения везде: куда уходят письма, решают настройки
- Миграция переносит существующие данные без потерь и не применяется, если не знает, кому их отдать

**Non-Goals:**

- Всё из раздела «Не делать» спеки: пароли, соцсети, коды, профиль, смена почты, удаление аккаунта, общий доступ, роли
- Защита от рассылки писем на много разных адресов с одного IP через форму. Лимит спеки — на почту, встроенный лимит Better Auth по IP — только для прямых запросов (см. Risks)
- Row-level security в PostgreSQL (см. «Владелец в каждом запросе»)
- Страница-посредник с кнопкой перед входом по ссылке (см. Risks про сканеры ссылок)

## Decisions

### Better Auth: magic link, Drizzle, своя таблица пользователей

- `better-auth` 1.7.24, плагины `magicLink` и `nextCookies` (последним). Конфиг — `src/auth/auth.ts` (server-only), обработчик — `src/app/api/auth/[...all]/route.ts` через `toNextJsHandler`
- Адаптер Drizzle с нашим `db`, `usePlural: true`: таблицы `users`, `sessions`, `accounts`, `verifications` — во множественном числе, как `contacts` и `groups`. Схему таблиц один раз генерирует CLI Better Auth той же версии (`pnpm dlx auth@1.7.24 generate`), результат кладём в `src/db/schema.ts`; сам CLI в зависимости не попадает
- `magicLink({ expiresIn: 15 * 60, storeToken: "hashed", sendMagicLink })`: ссылка живёт 15 минут, в базе — только хеш токена, так что бэкапы не содержат рабочих ссылок. Одноразовость встроена: токен удаляется атомарно при первой проверке, просроченный считается недействительным
- `session: { expiresIn: 30 дней, updateAge: 1 час }`: заход продлевает вход на 30 дней, но пишет в базу не чаще раза в час на устройство. Разница с «ровно 30 дней с последнего захода» — не больше часа
- `advanced.ipAddress.ipAddressHeaders: ["x-real-ip"]`: nginx ставит `X-Real-IP` сам и перезаписывает присланный клиентом, а `X-Forwarded-For` клиент может подделать
- `telemetry: { enabled: false }`: никакие сведения о приложении не уходят наружу
- Секрет — `BETTER_AUTH_SECRET`, адрес — `BETTER_AUTH_URL`, оба из настроек

Отвергнуто: свой вход на iron-session и своих токенах. Better Auth назван в спеке и уже даёт одноразовые токены, сессии в базе и выход с одного устройства.

### Почта, лимит и отмена старых ссылок

Хук `hooks.before` на путь `/sign-in/magic-link` срабатывает и для server action формы, и для прямого `POST /api/auth/sign-in/magic-link`:

1. Почта: `trim()` и `toLowerCase()`, затем общая схема `signInEmailSchema` (`src/lib/sign-in-email.ts`, ей же проверяет форма). Неверная → `APIError` с кодом `INVALID_EMAIL`, письма нет
2. Лимит: в транзакции с `pg_advisory_xact_lock(hashtext(email))` считаем строки `sign_in_link_requests` этой почты за последние 10 минут. Три и больше → `APIError` `TOO_MANY_REQUESTS`; прежние ссылки не трогаем. Иначе добавляем строку. Блокировка по почте не даёт двум одновременным запросам пройти четвёртым письмом. Строки старше 10 минут удаляются тут же, таблица остаётся крошечной
Хук возвращает в контекст нормализованную почту: дальше плагин создаёт токен и пользователя на неё.

Отмена старых ссылок происходит при записи нового токена, а не в предварительном хуке: PostgreSQL `BEFORE INSERT` trigger на `verifications` для строк `magic-link:%` берёт транзакционную advisory-блокировку по нормализованной почте и удаляет прежние строки magic link этой почты. Удаление и вставка нового токена выполняются в одной транзакции; при ошибке вставки удаление откатывается. Это сериализует одновременное создание токенов одной почты и не затрагивает другие виды проверок и другие адреса. Отклонённый лимитом запрос не создаёт токен и не отменяет действующую ссылку. Параллельные запросы проверяются тестом: после завершения остаётся только одна работающая ссылка.

Таблица `sign_in_link_requests`: `id`, `email`, `created_at`, индекс `(email, created_at)`. Отвергнуто: считать по `verifications` — старые ссылки мы удаляем, и счёт бы обнулялся. Отвергнуто: встроенный лимит Better Auth — он считает по IP и пути, а не по почте.

### Письма: Nodemailer, адрес — из `SMTP_URL`

- `nodemailer` 10.5.0, транспорт создаётся один раз из строки подключения `SMTP_URL` (`src/auth/mailer.ts`). Локально и в CI — `smtp://localhost:1025` (Mailpit), на сервере — `smtps://resend:<ключ>@smtp.resend.com:465`. Код один, отличаются настройки
- Содержимое письма собирает чистая функция `signInEmail(url)` → `{ from, subject, text, html }` (`src/auth/sign-in-email-message.ts`): отправитель `"Личная CRM" <noreply@mail.crm.volki-lzkv.ru>`, тема, кнопка «Войти», «Ссылка работает 15 минут», «Если вы не запрашивали вход — просто проигнорируйте письмо». HTML — простая таблица со встроенными стилями, у письма есть и текстовая версия. Отправитель — константа: он одинаков везде, Mailpit принимает любой
- Отправка не удалась → форма показывает «Не удалось отправить письмо, попробуйте ещё раз»; строка лимита при этом уже записана, то есть неудачная попытка тоже считается

Отвергнуто: HTTP API Resend через его SDK. Спека требует Nodemailer, а SMTP позволяет переключать заглушку и Resend одной настройкой без второй библиотеки.

### Mailpit

`axllent/mailpit:v1.33.1` — сервис `mailpit` в `docker-compose.yml`, порты `127.0.0.1:1025` (SMTP) и `127.0.0.1:8025` (страница в браузере и API). В CI — сервис с теми же портами в джобах Vitest и Playwright. Тесты читают письма через REST API Mailpit обычным `fetch`, без библиотеки: помощник `src/test/mailpit.ts` находит последнее письмо на адрес, пришедшее после начала теста, и достаёт из него ссылку. Тестовые адреса уникальны для теста, поэтому тесты не мешают друг другу и письмам, которые вы смотрите руками.

### Владелец в каждом запросе

- `contacts.user_id` и `groups.user_id` — `text not null`, внешний ключ на `users.id` с `on delete cascade`. У `notes` и `contact_groups` своего владельца нет: заметка принадлежит владельцу контакта, связь — владельцу контакта и группы
- Каждая экспортируемая функция в `src/db/queries.ts`, `contacts.ts`, `groups.ts` первым параметром принимает `userId` и добавляет условие `user_id = userId`. Для заметок — условие через контакт (`contact_id in (select id from contacts where user_id = …)` или join). TypeScript не даст вызвать функцию без владельца
- `setContactGroups`, `setContactGroupMembership`, `addContactToNewGroup`: связь создаётся, только если и контакт, и группа принадлежат `userId`; чужие id молча пропускаются, как уже пропускаются удалённые группы
- `findOrCreateGroup` и уникальность: индекс `groups_name_key` заменяется на `groups_user_id_name_key` по `(user_id, lower(name collate "ru-x-icu"))`. Поиск существующей группы по названию — тоже в пределах пользователя
- Индекс `contacts_user_id_name_idx` по `(user_id, name collate "ru-x-icu", id)` — под сортировку и курсор списка внутри одного пользователя
- Запрос с номером чужой записи ведёт себя как запрос несуществующей: чтение отдаёт `undefined` → `notFound()`, изменение ничего не меняет

Отвергнуто: row-level security в PostgreSQL. Она надёжнее как второй рубеж, но требует передавать пользователя в каждое соединение пула, а Drizzle и тесты с этим заметно усложняются. Явный `userId` плюс тесты «чужого» на каждую функцию — проще и проверяемо.

### Сессия на сервере: proxy, слой доступа, server actions

- `src/proxy.ts` (в Next.js 16 это бывший middleware, работает на Node.js): на каждый запрос страницы, кроме открытых без входа, вызывает `auth.api.getSession({ headers, returnHeaders: true })`. Сессии нет → редирект на `/login`. Есть → `NextResponse.next()` с переданным `Set-Cookie`: так продлённая сессия попадает в куку, а в серверных компонентах писать куки нельзя. Матчер не пускает proxy к `_next/static`, `_next/image`, `favicon.ico`, картинке превью; в коде — список открытых путей: `/login`, `/login/link-expired`, `/api/auth/*`, `/health`
- Proxy — только первый рубеж, как советует документация Next.js. Слой доступа `src/auth/session.ts`: `getCurrentUser()` читает сессию через `auth.api.getSession({ headers: await headers() })` и возвращает `{ id, email }` или делает `redirect("/login")`. Его вызывают все страницы и все server actions, включая `loadReminders` и `loadContactsPage`. `userId` никогда не приходит из браузера
- Чтение сессии — внутри уже существующих `<Suspense>` страниц, как требует `cacheComponents`

Отвергнуто: только оптимистичная проверка куки в proxy без базы. Она дешевле, но не может продлить куку, и вход обрывался бы через 30 дней после первого входа, а не после последнего захода. Запрос сессии к базе на каждую страницу для личной CRM незаметен.

### Страницы и шапка

- Группы маршрутов: `src/app/(app)/` — главная, карточка, «Группы», их layout с `Reminders` и шапкой с почтой и «Выйти»; `src/app/(auth)/login/` — вход и `link-expired`, их layout с прежней шапкой. Корневой layout оставляет `<html>`, шрифты, сетку и метаданные превью — превью ссылки в мессенджерах не меняется
- `SiteHeader` получает правую часть как `children`. В `(app)` — серверный `UserMenu` под `<Suspense>`: почта с `truncate` и кнопка «Выйти». В `(auth)` — «ДЛЯ ЛОГИСТОВ»
- Форма входа — клиентский компонент с `useActionState` и server action `requestSignInLink`. Action проверяет почту той же схемой, вызывает `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/link-expired" }, headers })` и переводит коды ошибок в тексты: `INVALID_EMAIL` → «Проверьте адрес почты» под полем, `TOO_MANY_REQUESTS` → «Слишком часто, попробуйте через несколько минут», прочее → «Не удалось отправить письмо, попробуйте ещё раз». Успех → «Ссылка для входа отправлена на <нормализованная почта>», форма остаётся
- `/login/link-expired`: «Ссылка устарела, запросите новую» и кнопка-ссылка «Получить новую ссылку» на `/login`. Better Auth ведёт сюда при любой ошибке проверки ссылки: использована, просрочена, отменена
- «Выйти» — server action `signOut`: `auth.api.signOut` удаляет сессию этого устройства, `nextCookies` стирает куку. Потом клиент делает полную навигацию на `/login` (`location.replace`), чтобы в клиентском кеше роутера не осталось страниц с контактами и «Назад» не показал их
- `src/app/(app)/contacts/[id]/not-found.tsx` — «Контакт не найден». Срабатывает и для чужого, и для несуществующего номера
- Пустой список: «Пока нет ни одного контакта. Добавьте первый контакт.»

### Миграция данных и почта владельца

Одна миграция `drizzle/0005_*.sql`: сгенерированная часть плюс ручной блок данных:

1. Таблицы `users`, `sessions`, `accounts`, `verifications`, `sign_in_link_requests`
2. `contacts.user_id` и `groups.user_id` — сначала nullable
3. Блок `DO`: если в `contacts` или `groups` есть строки, берёт почту владельца из `current_setting('crm.owner_email', true)`, делает `lower(trim(…))`. Пусто → `raise exception` с понятным текстом: вся транзакция миграций откатывается, `deploy.sh` останавливается, новый образ не стартует. Иначе создаёт пользователя с этой почтой (`email_verified = true`, имя пустое) и проставляет его id всем контактам и группам
4. `user_id` → `not null`, внешние ключи, новые индексы, замена уникального индекса групп

Почта владельца — настройка `OWNER_EMAIL`. `migrate.mts` перед миграциями выполняет `select set_config('crm.owner_email', $1, false)` на своём единственном соединении. На сервере `compose.yaml` передаёт `OWNER_EMAIL` контейнеру `crm-migrate`. Локально `pnpm db:migrate` запускает тот же `migrate.mts` с `.env`, вместо `drizzle-kit migrate`, чтобы локальная база переезжала так же, как серверная. Тестовые базы пустые, им почта не нужна.

Когда владелец потом входит по ссылке, Better Auth находит существующего пользователя по почте и не создаёт нового.

Отвергнуто: почта в коде миграции — она попала бы в публичный репозиторий. Отвергнуто: данные первому вошедшему — их мог бы забрать не владелец. Отвергнуто: перенос данных в `migrate.mts` на TypeScript после миграций — колонка стала бы `not null` только следующей миграцией, и между ними были бы записи без владельца.

### Тестовые данные

`pnpm db:seed` находит или создаёт пользователя `OWNER_EMAIL` и создаёт контакты, заметки и группы с его `user_id`. Без `OWNER_EMAIL` — понятная ошибка.

### Настройки

| Настройка | Компьютер (`.env`) | Сервер | CI и e2e |
|---|---|---|---|
| `BETTER_AUTH_SECRET` | своя случайная строка | `.env` на сервере | тестовое значение в workflow |
| `BETTER_AUTH_URL` | `http://localhost:3000` | прямо в `compose.yaml`: `https://app.volki-lzkv.ru` | `http://localhost:3000`, e2e — `http://localhost:3200` в `playwright.config.ts` |
| `SMTP_URL` | `smtp://localhost:1025` | `.env` на сервере: Resend | `smtp://localhost:1025` |
| `OWNER_EMAIL` | ваша почта | `.env` на сервере | не нужна |

В `compose.yaml` `BETTER_AUTH_SECRET` и `SMTP_URL` обязательны (`${…:?…}`). Без них любая команда compose падает, и выкатка останавливается на первом же шаге, до бэкапа и миграций, а прод работает на прежней версии. `OWNER_EMAIL` необязательна для compose: её отсутствие при непустой базе ловит сама миграция. Сборке образа в `Dockerfile` нужен фиктивный `BETTER_AUTH_SECRET` — как фиктивный `DATABASE_URL`: настоящие значения приходят только при запуске.

### Тесты

- Vitest, правила входа: запросы идут через `auth.handler(new Request(...))` — это и есть «запрос не из формы» — и через `auth.api`, письма читаются из Mailpit. Время не ждём, а сдвигаем в базе: `expires_at` токена (14 и 16 минут), `created_at` строк лимита (11 минут), даты сессии (29 и 31 день)
- Vitest, данные: у каждой функции `src/db` — тест «чужого»: два пользователя, запрос от B с id записей A. Фабрики получают владельца: `makeUser(email)` и `userId` в `makeContact`, `makeGroup`
- Vitest, миграция: временная база `*_migration_test`. Применяем миграции до `0004` (копия журнала без новых записей), кладём контакты, заметки, группы и связи, затем применяем остальное с почтой владельца и без неё. Сверяем числа строк до и после
- e2e: фикстура `signIn(page, email)` проходит настоящий вход: форма → Mailpit → ссылка. `main-scenario` и `keep-in-touch` входят ею перед сценарием и кладут строки в базу с `user_id` вошедшего. Новые `e2e/sign-in.spec.ts` — сценарии входа и шапки, `e2e/data-ownership.spec.ts` — критерий успеха спеки (A и B)
- Встроенный лимит Better Auth по IP (5 запросов в минуту на вход по ссылке) мешал бы e2e: все входы идут с одного адреса. Фикстура e2e даёт каждому тесту свой заголовок `X-Real-IP`. Приложение везде одно и то же, лимит остаётся включённым

## Risks / Trade-offs

- [Почтовые сканеры (Outlook Safe Links, корпоративные фильтры) открывают ссылки из писем заранее и «съедают» одноразовую ссылку] → пользователь увидит «Ссылка устарела» и запросит новую. Если начнёт мешать — отдельной правкой добавить страницу с кнопкой «Войти» перед входом
- [Ссылка открыта на другом устройстве, не там, где запрашивали] → вход выполнится на том устройстве, где открыли. Так и задумано спекой: «Открыл ссылку — я внутри»
- [С одного IP через форму можно запросить письма на много разных адресов] → лимит спеки — на почту, встроенный лимит по IP не действует на server action. Resend на бесплатном тарифе ограничит отправку сотней писем в день. Если станет проблемой — лимит по IP в хуке отдельной правкой
- [Порт 465 закрыт с сервера] → проверить `nc -zv smtp.resend.com 465` с сервера до выкатки. Resend принимает и на 2465/587/2587
- [Письма Resend попадают в спам] → домен с DKIM и SPF, проверенный в Resend; первые письма проверить в своём ящике
- [Запрос сессии к базе на каждую страницу] → для одного-нескольких пользователей незаметно; при росте — кеш сессии в куке (`session.cookieCache`)
- [Миграция меняет существующие данные] → бэкап перед миграцией уже делает `deploy.sh`; миграция в одной транзакции; без почты владельца она не применяется. Показать миграцию вам до merge — отдельная задача
- [Откат одной командой `rollback.sh` больше не работает: старая версия не умеет писать контакты без `user_id`] → откат только вместе с базой, см. Migration Plan
- [Выйти на всех устройствах сразу нельзя] → в спеке выход только на этом устройстве; потерянное устройство — пока только через базу, отдельной правкой

До merge:

2. Вы: аккаунт в Resend, домен `mail.crm.volki-lzkv.ru` в Resend, его записи DNS у регистратора, дождаться «Verified», ключ с правом только на отправку

4. Проверить с сервера порт 465 до Resend

Выкатка — обычная: merge → образ → бэкап базы → миграции → новый образ → `/health`. После неё: войти под своей почтой на https://app.volki-lzkv.ru, увидеть все прежние контакты, сверить числа.

Откат — только вместе, запускаете вы:

1. `rollback.sh` — возвращает прошлый образ. Он стартует, но с новой схемой база ему не подходит
